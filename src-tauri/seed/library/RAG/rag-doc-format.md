# RAG 문서 작성 규칙

에이전트가 검색해서 바로 답을 찾을 수 있는 지식 문서의 형식이에요. 프로젝트 `docs/`를 이 형식으로 쓰면, 에이전트가 파일 이름이나 키워드로 찾아 한 문서만 읽고도 답할 수 있어요.

## 원칙

- **주제 하나에 파일 하나.** 한 파일이 여러 기능을 다루면 검색 결과가 흐려진다
- **결론 먼저.** 첫 단락만 읽어도 답이 되게
- **코드 이름은 그대로.** 파일, 함수, 명령, 설정 키를 `코드 표기`로 적어 검색에 걸리게 한다
- **고정된 구역.** 모든 문서가 같은 순서의 제목을 가지면 필요한 부분만 잘라 읽을 수 있다
- **최신으로.** 코드를 바꾸면 같은 변경에서 문서도 고치고 날짜를 바꾼다

## 형식

```markdown
---
title: 기능 이름
area: 영역 (canvas, agents, ui …)
status: done | partial | planned | dropped
files: [이 기능의 주요 파일]
related: [관련 문서 경로]
updated: YYYY-MM-DD
---

# 기능 이름

## 요약
두세 문장. 무엇이고 어디에 있나.

## 동작
사용자가 보는 것. 버튼, 단축키, 상태.

## 구현
어느 파일의 어떤 함수가 무엇을 하나. 데이터가 어디 저장되나.

## 결정 기록
왜 이렇게 했나. 버린 대안.
```

## 폴더

- `docs/README.md`: 폴더 지도와 이 형식 설명
- `docs/features/<영역>/<기능>.md`: 기능별
- `docs/architecture/`: 여러 기능에 걸친 구조
- `docs/reference/`: 표로 정리한 목록(명령, 저장 위치, 설정)
